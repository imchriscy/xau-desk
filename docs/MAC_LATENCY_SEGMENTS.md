# Mac 延迟分段模型 · 现状与可选演进

> **当前 Mac 生产路径**：文件桥 + `XauDeskBridge`（**不**启用 `ipc/` DLL、不默认 1ms 定时器）。  
> **网络 / VPS**：后期优化，本文只写清概念与搁置方案。

---

## 1. 建议的三段划分（便于讨论，不是三条独立网线）

| 段 | 名称 | 典型量级（你当前环境） | 可优化？ |
|----|------|------------------------|----------|
| **① 本机栈** | XauDesk UI → 网关 → 桥文件 → EA → **调用 `OrderSend()` 之前/调用的本地部分** | Mac 粗算 **~15–40 ms**（顺利时）；EA 内「读到文件→`OrderSend` 前」实测 **~0.87 ms** | **能**，见下文「搁置方案」 |
| **② 终端↔券商** | MT5 进程经 **一条 TCP 交易通道** 到券商撮合服务器（含你家里的光纤/Wi‑Fi、运营商、跨境路由） | MT5 右下角常显 **~200–250 ms**（与压测 `OrderSend` 段 ~245 ms 一致） | **主要**靠 **VPS / 换接入点 / 券商机房**，不是改 XauDesk UI |
| **③（可选）远程 UI** | 人不在本机时：笔记本 ↔ 家里 Mac / VPS 的 **远控或 HTTP** | 视 Tailscale/RDP/5G 而定 | 与下单无关时常可忽略；**远程只当 UI** 时，② 仍在跑 MT5 的那台机器上发生 |

### 重要：没有单独的「网线 → MT5」第三段（本机操盘时）

当 **XauDesk 与 MT5 在同一台 Mac**（Wine 终端 + Electron）时：

- **① 全程不走公网**：`127.0.0.1` + `Common/Files` 写盘，**不消耗家宽「到 MT5」的 RTT**。
- **② 已包含家宽**：`OrderSend` 发出的包从 **本机 MT5** 出发，经你家路由器/运营商到券商。  
  MT5 显示的 **243 ms** 就是 **「这台电脑上的 MT5 → 券商服务器」** 的往返，**不是**再加一层「电脑网速」。

因此：

- **不要**把「家宽」从 ② 里再拆出一条「第三段网线延迟」去单独优化——它和 ② 是 **同一路径**。
- 换千兆/更好 Wi‑Fi 若只能省 **几 ms**，对 **200 ms 级跨境 RTT** 通常 **几乎无感**；有意义的 jump 是 **把 MT5 挪到离券商近的 VPS**（② 变成 **~0.5–2 ms**）。

```text
【本机 Mac 日常】

  XauDesk ──① 本机──▶ EA ──OrderSend──▶┐
                                        ├── ② 互联网 ──▶ 券商（~243ms）
  （家宽只参与 ②，不参与 ①）

【日后 VPS 拓扑】

  Mac/XauDesk ──③ 远程 UI？──▶ VPS 上的 MT5 ──②'──▶ 券商（~0.5ms 级）
```

## 2. ① 里再拆开：别把 0.87 ms 当成整段

| 子步骤 | 量级 | 说明 |
|--------|------|------|
| UI / HTTP / 写 `xau_trade.json` | ~几–十几 ms | ① 的一部分 |
| 等 EA **16 ms 定时器** 扫文件 | **0–16 ms**（均 ~8） | 与 **0.87 ms** 串联，不矛盾 |
| EA 读到文件 → `OrderSend()` 调用前 | **~0.87 ms** | 压测中位；**不是**全链路亚毫秒 |
| 网关 **25 ms** 轮询 ack | **0–25 ms** | 影响「UI 收到 ok」，不影响券商是否成交 |

**结论**：① 到「发出委托」粗算 **~15–40 ms** 合理；**不是**亚毫秒整段。见 [artifacts/latency-summary-20251116.md](artifacts/latency-summary-20251116.md)。

## 3. 搁置的本机架构升级（暂不实施，保留可能）

目标：**把 ① 稳定压到 ~10 ms 内**（仍 **不含** ② 券商 RTT）。属于 **换代**，不是改两行 EA。

| 方向 | 思路 | 预期收益 | 代价 / 风险 |
|------|------|----------|-------------|
| **1 ms 定时器** | `InpRefreshMs = 1`（或 `OnTick` 补强） | 少 **~5–15 ms** 「等扫盘」 | Wine CPU、写盘频率 |
| **IPC 替代 JSON 下单** | `ipc/Mt5IpcBridge.dll` + UDS（见 [ipc/README.md](../ipc/README.md)） | 去掉写盘 + 部分轮询 | 维护 DLL、Wine 路径、与文件桥双轨 |
| **减少 ack 轮询** | 网关 `RPC_POLL_MS`→1，或 socket 回传事件 | UI 确认快 **~10–25 ms** | 实现复杂度 |
| **二进制快通道** | 复用 `fast-lane.mjs` :5192 + 与 Bridge 合并 | 下单路径与 Windows 执行 EA 对齐 | Mac 主路径今日未接 |

**触发条件（建议）**：② 已通过 VPS 压到 **个位数 ms**，且策略 **真的吃 ① 的 10 ms 级**；否则优先 **VPS / 线路**，不动本项。

复现压测（默认关闭）：

```bash
XAU_LATENCY_TRACE=1 npm run gateway:mac
npm run latency:watch   # npm run latency:analyze
```

## 4. Windows ① 与「5 ms 极限」能否成立？

### Windows 第一段（软件 → `OrderSend` 调用，不等成交）

| 实现 | ① 粗算 |
|------|--------|
| 现网 Python `MetaTrader5` | **~数–数十 ms** |
| Rust/DLL + 共享内存（规划） | 热路径 **~0.05–2 ms** 量级（**进程内段**可亚毫秒） |

### ② VPS 后（MT5 与券商同机房）

- 官方宣传 **~0.52 ms** 指 **终端 ↔ 交易服务器 ping**，属 **②**，不是全链路保证。

### 「① + ② 精准 ≤ 5 ms」？

**不能作为零售 MT5 的可靠 SLA**，只能作 **理想实验室上界**：

| 环节 | 乐观 |
|------|------|
| ① Win 优化栈 | **1–5 ms** |
| ② VPS↔券商 | **0.5–2 ms** |
| 券商撮合 / 流动性 / 重试 | **1–50+ ms**（市场决定） |

因此：

- **机器侧**在 VPS + 极致本机栈下，**有机会**做到「点击 → 服务器收到委托 **个位数 ms**」。
- **「成交确认 / 持仓出现在手机」** 仍可能 **> 5 ms**，且 **无法** 用软件单方面压到恒定 5 ms。
- Mac 文件桥 **不配** 和 Win 亚毫秒 ① 对标；Mac 当前目标是 **① ~几十 ms 可用 + 产品省心**，见 [MAC_EASY_CONNECT.md](MAC_EASY_CONNECT.md)。
